## 1. 결론과 파일의 관계

**받은 v2는 기존 SDK를 대체하는 완성본이 아니라, 기존 팔 SDK에 손 제어를 추가하는 패치다.** 손 제어의 기본 구조는 사용할 만하지만, 재접속 시 초기 목표, 응답의 유효성 판정, 펌웨어 재생성 과정은 수정하고 통합해야 한다.

| 대상 | 실제 구성 | 통합할 때의 역할 |
|---|---|---|
| `humanoid_sdk-main/` | 기존 전체 SDK, 캐시 제외 40개 파일 | 팔 제어와 bringup의 기준본 |
| `humanoid_sdk V2/` | 20개 파일: 손 패키지 신규 18개, bringup 수정 2개 | 기존 전체 SDK 위에 반영할 추가분 |
| 루트 `README.md` | 기존 SDK README에 손 패키지·빌드·테스트 안내 추가 | 통합 SDK의 README로 반영할 문서 |
| `dexhand_firmware_v2.zip` | 응답 기능을 추가한 양손 ESP32 코드, 공통 템플릿, C++ 검사 | PC의 v2 응답 기능과 짝을 이루는 펌웨어 |
| `dexhand_control/` | 기존 PC 송신기, JSON 보정값, v1 펌웨어·생성기·문서 | 원본 보정값 및 기존 동작과 비교할 기준 |

v2 폴더에는 `bhl_arm_sdk`, bringup의 `package.xml`·`setup.py`, `demo.launch.py`, `remote.launch.py`, `env.sh` 등이 없다. **v2 폴더만 남기고 기존 SDK를 교체하면 안 된다.** 기존에만 있는 38개 파일은 삭제 대상이 아니다.

## 4. 펌웨어와 프로토콜 비교

`dexhand_firmware_v2.zip`은 임시 폴더에 풀어서 기존 업로드용 코드와 비교했다.

| 부분 | 비교 결과 |
|---|---|
| 양손 `BoardConfig.h` | 각각 기존 파일과 SHA-256이 완전히 같음: 핀·보정 범위 유지 |
| 양손 `ServoOutput.h` | 각각 기존 파일과 SHA-256이 완전히 같음: LEDC 출력 방식 유지 |
| `.ino` | CAN 송신 큐·상태 송신·PING 처리 및 상태 오류 수집 추가 |
| `PoseReceiver.h` | 기존 5프레임 조립에 거부 사유·채널 기록 추가 |
| `HandController.h` | APPLIED·REJECT·CONTROL_ACK·heartbeat, 횟수·플래그 보고 추가 |
| `StatusReport.h` | 새 응답 프레임 형식과 코드 |
| 생성기·공통 소스 | 새 도구가 있으나 실제 패키지 경로와 불일치. 아래 문제 6 참조 |

이 비교 당시 왼손 프로필 태그는 `c3c778d2`, 오른손은 `c7b282e4`였다. 이후 배선 수정으로 현재 태그는 달라졌으며 [현재 프로토콜 명세](PROTOCOL_v3.md)를 따른다. 받은 YAML의 양손 풀림·당김 값도 당시 JSON의 해부학적 CAN 순서와 일치한다. 오른손에서 과거 사용한 모터 식별 번호와 CAN 배열 순서는 구별해야 한다.

| 방향 | 종류 | 왼손 node 60 | 오른손 node 61 | v1과 관계 |
|---|---|---:|---:|---|
| PC → ESP32 | CONTROL | 0x03C | 0x03D | 같은 형식 |
| PC → ESP32 | POSE | 0x33C | 0x33D | 같은 형식: 순번·그룹·3개 uint16 µs, 총 5프레임 |
| PC → ESP32 | PING | 0x23C | 0x23D | 신규 |
| ESP32 → PC | STATUS | 0x2BC | 0x2BD | 신규 |
| ESP32 → PC | PONG | 0x1BC | 0x1BD | 신규 |

팔 노드 1~10과 손 노드 60·61은 현재 설정에서 충돌하지 않는다. 양손 50Hz의 POSE는 초당 500프레임, 세트별 STATUS는 약 100프레임이다. 프레임당 135비트 근사라면 손 관련 약 8.1%/1Mbps이며, **팔 트래픽·진단·제어 프레임·오류 재전송은 별도**다. 전체 부하와 지연은 실제 팔 송수신 주기로 측정해야 한다.

기존 송신기는 v2 펌웨어의 CONTROL·POSE와 호환된다. 반대로 **v2 SDK의 기본 `protocol: 2`는 응답하는 v2 펌웨어가 필요**하다. 기존 v1 손을 사용하면 PONG을 못 받아 enable이 실패한다. 임시 v1 호환 설정은 `protocol: 1`이며, 이 경우 수신·출력 적용 확인 기능은 없다.

APPLIED는 ESP32가 목표를 검사하고 LEDC 출력 값을 기록했다는 뜻이다. 서보의 실제 위치, 힘, 전류, 물체를 잡았는지는 확인하지 못한다. 전원 투입 시 자동 실행, 첫 완성 세트 적용, 통신 단절 시 마지막 PWM 유지라는 기본 구조는 유지된다. ROS 노드는 별도로 enable을 기다린다.

## 5. 재현한 결함과 수정 우선순위

### 1) 우선 수정: SDK 재활성화가 기존 파지 자세를 펼침으로 바꿈

위치: 수신 SDK `controller.py:69`, `controller.py:209`, `controller.py:233`; `cli.py`의 첫 목표 구성.

새 컨트롤러의 goal·command는 기본 open이다. enable은 손의 PWM_ON을 보면 START 대신 RESUME을 선택하지만, 곧바로 goal을 command에 복사하고 첫 목표를 전송한다. 따라서 ESP32가 이미 물체를 잡고 있어도 SDK를 새로 실행해 enable하면 **첫 목표가 펼침으로 바뀐다. 이 첫 변경은 속도 제한도 거치지 않는다.** CLI의 grip 명령도 먼저 open을 보낸다.

실제 받은 HandController와 가상 CAN FakeHand로 재현: 오른손 power 자세 → RESUME → APPLIED → PWM 목표가 전체 open으로 교체됐다. 실물이 아니라 가상 버스에서 확인한 결과다.

수정 방향: 재접속 시 기존 목표를 모르는 상태와 명시적 자세 변경을 구분한다. ESP32의 마지막 명령을 읽어 동기화하거나, 새 초기 목표의 명시적 지정 전에는 유지한다. 읽는 값도 실제 측정 위치가 아닌 마지막 명령임을 표시해야 한다. 현재는 보정 프로필 태그만 읽을 수 있어 기존 파지 자세를 복원할 정보가 부족하다.

### 2) 오래된 APPLIED 반복 수신이 통신 LOST 판정을 막음

위치: `controller.py:107`~`125`, `controller.py:310` 이후.

현재 기다리는 순번과 다른 APPLIED를 모두 늦게 온 성공으로 보고 `missed=0`으로 만든다. 해당 순번이 실제 미확인 송신 목록에 있는지, 이미 처리한 응답인지 확인하지 않는다.

재현: 새 목표 20개에 대한 확인은 전혀 없는데, 같은 과거 순번·횟수의 APPLIED를 반복 공급하니 `live=True`, `missed=1`, `late=20`이 됐다. 설정된 연속 실패 한도는 10이었다. 정상 CAN이 저절로 이런 프레임을 만든다는 뜻은 아니며, 중복·재생·다른 송신자 등에 대한 판정 결함이다.

수정 방향: 송신 시각·세션·미확인 순번을 관리하고, 중복·이미 확정된 응답은 연결 상태를 회복시키지 못하게 한다. 새 적용 횟수와 실제 미확인 명령의 진행을 함께 확인한다.

### 3) 잘못된 속도 설정을 받으면 목표와 반대로 움직임

위치: `config.py:122` 이후, `controller.py:315`~`316`.

기본값 `max_speed: 2.0`은 정상이다. 다만 YAML을 `max_speed: -2.0`으로 바꿔도 로더가 허용한다. 음수 max_step을 사용한 clamp 계산 때문에 open 목표를 유지해도 모든 command가 증가한다.

재현: 20ms 간격 13회 후 goal은 모두 0인데 command는 모두 약 0.52가 됐다. 엄지 13·14번 합이 1.04로 설정된 제한 1을 넘었다. 입력 목표 검사와 별개로 내부 보간 출력 검사가 빠져 있다.

수정 방향: 속도·주기·대기시간·실패 한도·제약값에 유한값 및 범위 검사를 추가하고, 실제 송신 직전 command에도 제약을 적용한다. 보정 끝점과 허용 PWM 범위도 설정 단계에서 검증한다.

### 4) ESP32 재부팅을 ACK 65,036개 손실로 오인

위치: `controller.py:119`~`125`, STATUS·PONG 형식.

적용 횟수를 16비트 순환 차이로만 계산한다. 재부팅으로 500에서 0으로 초기화된 경우 `acks_lost=65036`이 됐다. 현재 응답에는 boot_id·uptime이 없어 재부팅과 정상 순환을 확실하게 구분할 수 없다.

수정 방향: 부팅·세션 식별과 재동기화 절차를 설계한다. 프로토콜 변경 전에는 시간·허용 증가량으로 불가능한 점프를 감지하고 통계를 분리한다. 8비트 순번은 50Hz에서 5.12초마다, 16비트 적용 횟수는 약 21.8분마다 순환한다.

### 5) 형식 오류로 거부한 동일 순번이 나중에 APPLIED됨

위치: v2 `DexHandLeft/PoseReceiver.h:25`~`30`; 오른손과 공통 소스에도 같은 로직.

잘못된 버전·그룹을 받으면 거부 사유만 기록하고 순번을 차단하지 않는다. 실제 v2 C++ HandController에 순번 9의 잘못된 헤더를 두 번 준 다음, 같은 순번의 정상 5개 그룹을 주면 **REJECT_FORMAT → REJECT_FORMAT → APPLIED**가 발생했다.

문서는 순번당 결과 한 번, 거부한 나머지 프레임 폐기를 약속한다. 현재 구현은 그 약속과 다르다. PC가 거부를 보고 중단해도 이미 전송 중인 같은 세트의 나머지가 적용될 수 있다.

수정 방향: 형식 오류도 순번의 신구 판정·거부 래치에 통합하고, 같은 순번에 최종 결과가 둘 이상 생기지 않도록 검사한다.

### 6) 펌웨어 재생성 도구가 실행되지 않음 / 구 도구 사용 시 v1로 돌아감

위치: ZIP의 `tools/make_sketches.py:7`~`8`, 양손 `.ino:3`, 기존 `tools/prepare_firmware.py`.

새 도구는 `firmware/common`과 `firmware/DexHand.ino.in`을 찾는다. 실제 압축파일에는 `DexHandCan_shared/`가 있다. 실행 결과 템플릿 경로에서 FileNotFoundError가 발생했다. 경로만 바꾸더라도 공통 폴더에 복사 대상 ServoOutput.h가 없다.

또한 v2 .ino의 주석은 기존 prepare_firmware.py 실행을 안내한다. 기존 생성기는 여전히 v1 공통 코드를 사용한다. 양손 스케치만 v2로 바꾼 뒤 이 도구를 실행하면 응답 기능이 없는 v1 코드로 다시 생성된다.

수정 방향: v2 공통 소스·보정 원본·생성기 경로를 하나로 정리하고, 생성 결과 재현 검사와 양손 빌드를 묶는다. CONTROL·POSE·PING 외 STATUS·PONG ID도 사용자 요구대로 스케치 상단 상수에 드러내는 것이 좋다.

## 6. 통합 시 남아 있는 부분

- `robot.launch.py`에는 손 선택이 추가됐지만 `demo.launch.py`는 `hands`·`hand_config`를 전달하지 않는다. 기존 demo 실행만으로 양손이 올라오지 않는다.
- 기존 bringup `package.xml`에는 손 패키지 의존성 추가가 없다. 선택 기능으로 유지할지, 통합 배포의 필수 의존성으로 할지 정해야 한다. 수동으로 전부 빌드한 환경과 자동 의존성 설치 환경을 구분해야 한다.
- 손은 팔의 `estop=true`만 따라간다(`node.py:128`). 팔의 개별 MODE_LOST·LOST는 estop이 false일 수 있어 손이 계속 움직일 수 있다. 손 고장이 팔을 멈추는 역방향 연동도 없다. 작업별 유지·정지 정책을 가진 상위 관리자가 필요하다.
- 상위 AI·조작 프로그램의 목표 갱신이 끊겨도 손 노드는 마지막 목표를 계속 송신한다. ESP32 통신 watchdog과 상위 명령 유효시간은 다른 문제다. 상위 명령 만료·제어권 정책은 미구현이다.
- CLI와 ROS 노드 등 여러 송신자의 제어권을 막는 기능은 없다. 같은 손에 동시에 명령하지 않도록 운영 규칙만으로 의존하지 않게 해야 한다.
- 펌웨어의 넘침·복구 플래그는 `twai_transmit(..., 0)`의 큐 등록 성공 시 지워진다(`HandController.h:147`). PC 수신 확인은 아니다. 큐 등록 후 bus-off 등으로 유실되면 PC가 해당 이력을 못 볼 수 있다. 중요한 오류는 누적 횟수나 명시적 해제 정책이 필요하다.
- 최초 CAN 시작에도 CAN_RECOVERED가 설정되는 경로가 있다. 정상 부팅과 장애 복구의 의미를 구분하는 편이 진단에 좋다.
- 손 목표를 실제 joint_states로 발행하지 않는 것은 타당하다. 이후 시각화가 필요하면 명령 기반 추정 표시와 실제 측정값을 구분해야 한다.

## 7. 팔이 떨어지는 문제와의 관계

**이번 v2는 팔의 힘·게인·중력 보상·전류 한도·위치 유지 로직을 바꾸지 않는다.** 따라서 v2 손 패키지를 반영해도 기존 팔의 드르륵거림·낙하 원인이 해결됐다고 볼 수 없다.

기존 SDK의 POSITION, MODE·ERROR 확인, 감속비 검사, 전류 제한 읽기, 게인 확인 기능을 유지하면서 실기 로그로 원인을 구분해야 한다. 22A는 전달받은 값일 뿐이며 이번 오프라인 검토로 보드의 실제 설정을 확인한 것은 아니다. DexHand의 실제 질량·무게중심도 아직 확인되지 않았다. 임의의 전류·게인 상향값을 이 검토에서 제시하거나 반영하지 않았다.

## 9. 직접 개발할 때 권장하는 순서

1. 기존 전체 SDK를 기준으로 손 패키지·bringup·README를 합친 한 개의 개발본을 만든다. 기존 팔 진단 개선을 보존한다.
2. 재활성화 초기 목표, ACK 유효성·재부팅 처리, 설정 검증, 형식 거부 래치를 먼저 수정한다. 각 결함의 재현을 회귀 검사로 만든다.
3. JSON 보정값에서 YAML·BoardConfig를 함께 생성하도록 하고, v2 공통 소스·생성기를 통합한다. 재생성이 v1로 돌아가지 않게 검사한다.
4. demo·실기 launch와 배포 의존성을 정리하고, 팔·양손 정지 정책 및 명령 제어권을 설계한다.
5. ROS 2 환경에서 가상 CAN 왕복 → 모터 전원 없이 실제 CAN 응답 → 손 한 개 제한 동작 → 양손 → 팔·양손 동시 순서로 검증한다. 최초 목표와 물체 파지 중 재접속을 별도 확인한다.
6. 상위 VLA에는 손별 15개 당김 비율과 명령 유효시간을 노출하되, 관절 각도·실제 파지 피드백과 혼동하지 않는다. 학습 행동 공간을 더 작게 만들지는 상위 계층에서 결정한다.

검토 시점의 권장안은 **전체를 새로 버리고 만드는 것보다, 기존 팔 SDK를 유지하고 받은 손 제어를 수정해 통합하는 방식**이다. 실제 코드 통합·버그 수정·펌웨어 업로드는 이 비교 작업에서 수행하지 않았다.
